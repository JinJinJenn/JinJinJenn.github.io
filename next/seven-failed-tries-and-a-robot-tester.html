Seven failed tries and a robot tester

6 Nov 2026 · tooling

In this story 3 sections
  1. The tools
  2. Keeping failed runs away from real saves
  3. Checking that the test catches the original problem

Testing a Sims 4 mod by hand goes like this: install it, start the game, wait through the loading screens, load the save, click through six menus, look at the result, quit, tweak the code, repeat. My partner was doing that for the first couple of versions and got, understandably, frustrated.

So, very macho, I took over the testing. After two failed iterations I figured it was easy. Seven more failed iterations later I was just as annoyed, and I had learned how little those ten minutes of clicking told us each time. We built an automated tester to handle the repeated loading and clicking, which was a relief.

The tools

  • A launcher starts the game, waits through menus and loading screens, closes popups and loads a test copy of a save.
  • A tiny helper mod inside the game reads its state and runs commands, so a test can ask directly what type a lot is or whose money build mode spends instead of guessing from screenshots.
  • A scripted clicker drives the real menus like a player and takes a screenshot at every step.
  • Each run produces pass/fail checks alongside the screenshots. The park run recorded on 6 November 2026 passed all 28 checks.
  • A readable copy of the game's code lets us look things up instead of guessing, which was how we got to seven failures.

Keeping failed runs away from real saves

Some early runs went wrong in ways we hadn't expected. We added safeguards so we could recover from a failed test without putting the real saves at risk:

  • The harness refuses to start the game on anything but a renamed test copy of a save, checks which save actually loaded, and kills the game if it's the wrong one.
  • Killing the game mid-run once left its settings file empty, so the next start ran with every mod switched off. Now a full known-good copy of the settings is put back after every run.
  • Mods are copied in atomically and only while the game is closed (a half-copied mod crashed one early test), and whatever they replace is backed up first.
  • Any save the game attempts during a test is redirected away from the real slots.
  • If the PC's screen is locked, clicks and screenshots can't work, so the robot says so instead of clicking at nothing.
  • A random "new personality trait" dialog froze one run, so the game's own auto-answer switch is turned on during tests.
  • Every run leaves a journal and screenshots, so a failure can be replayed on paper instead of redone by hand.
  • My working notes and logs used to get deleted after 30 days, which made it easy to lose the "why did we do it this way?" trail while debugging a game for weeks. They're now kept for ten years, with a private backup copy.

Checking that the test catches the original problem

We also run the same test with the mod switched off, because it needs to catch the broken park setup before we can trust a passing result. That run fails as expected, while the run with the fix passes.

Now the question after every change isn't "does it feel right?" but "what did the run say?" It makes for a much calmer household.
