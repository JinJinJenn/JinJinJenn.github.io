Seven failed tries and a robot tester

6 Nov 2026 · tooling

Testing a Sims 4 mod by hand goes like this: install it, start the game, wait through the loading screens, load the save, click through six menus, look at the result, quit, tweak the code, repeat. My partner was doing that for the first couple of versions and got, understandably, frustrated.

So, very macho, I took over the testing. After two failed iterations I figured it was easy. Seven more failed iterations later I was just as annoyed, and had learned the real lesson: the problem wasn't the mod, it was that every attempt cost ten minutes of clicking and told us almost nothing. So we built an automated QA robot. Thank goodness.

The tools

  • A launcher that starts the game, waits through menus and loading screens, closes popups, and loads a test copy of a save.
  • A tiny helper mod inside the game that can read the game's state and run commands. Instead of guessing from screenshots, a test can ask the game directly: "what type is this lot? whose money does build mode spend?"
  • A scripted clicker that drives the real menus like a player, taking a screenshot at every step.
  • Checks and a verdict: a list of pass/fail checks, plus the screenshots. The park run recorded on 6 November 2026 passed all 28 checks.
  • The game's own research: a full readable copy of the game's code, so we can look things up instead of guessing (guessing was how we got to seven failures).

The recovery

Driving a game by robot means things can go wrong, so much of the work went into protecting real saves and making failed tests recoverable:

  • Test copies only. The harness refuses to start the game on anything but a renamed test copy of a save, checks which save actually loaded, and kills the game if it's the wrong one.
  • Settings get restored. Killing the game mid-run once left its settings file empty, so the next start ran with every mod switched off. Now a full known-good copy of the settings is put back after every run.
  • Safe installs. Mods are copied in atomically and only while the game is closed (a half-copied mod crashed one early test), and whatever they replace is backed up first.
  • Saves are fenced. Any save the game attempts during a test is redirected away from the real slots.
  • Locked screen? Stop. If the PC's screen is locked, clicks and screenshots can't work, so the robot says so instead of clicking at nothing.
  • Popups can't stall it. A random "new personality trait" dialog froze one run, so the game's own auto-answer switch is turned on during tests.
  • Everything is logged. Every run leaves a journal and screenshots, so a failure can be replayed on paper instead of redone by hand.
  • Keep the receipts. My working notes and logs used to get deleted after 30 days. Debugging a game for weeks, that's how you lose the "why did we do it this way?" trail. They're now kept for ten years, with a private backup copy.

The best part: a test that can fail

We also run the same test with the mod switched off. It must fail. If it passed, the test would be measuring nothing. It fails, the park shows up broken in the screenshots, and the real run goes green. The comparison below shows the same MoveAnywhere test without the mod and after the fix.

Now the question after every change isn't "does it feel right?" but "what did the run say?" It makes for a much calmer household.
